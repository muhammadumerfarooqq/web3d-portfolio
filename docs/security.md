## 1a. Contact system (P4): design and controls

**Flow.** Browser form → `POST /api/contact` (Vercel Function, Node, bom1) → validate → Turnstile → rate limit + store (one SQL call) → email. The time-trap stamp comes from `GET /api/contact-token` when the form renders.

| Layer | What it stops | How |
|---|---|---|
| Method / type / size | Probing, form-encoded CSRF posts, memory abuse | POST only (405), `application/json` only (415; a cross-site HTML form cannot send JSON), body ≤ 8 KB counted while streaming (413) |
| Same-origin check | Other sites spending the quota from their visitors' browsers | `Origin` (or the `Referer` origin) must be the production domain, the alias, this project's preview URLs or localhost (403). No CORS headers are ever sent, so cross-origin scripts cannot read responses |
| Shared zod schema | Bad data, script payloads, header injection | The same schema runs in the browser and on the server: lengths, a subject allow-list, trimmed values, control characters rejected everywhere, CR/LF and Unicode line breaks rejected in every field that reaches a header (name → Subject, email → Reply-To). `buildMail` re-checks, and the body is plain text only (no HTML email, so no HTML injection) |
| Honeypot | Naive form-filling bots | A hidden `website` field; if filled, the server answers 200 and drops the message (the bot learns nothing) |
| Time trap | Instant scripted posts | `GET /api/contact-token` returns `timestamp.HMAC-SHA256(timestamp, hashed IP)` keyed with `IP_HASH_SALT`; the post must come ≥ 3 s and ≤ 2 h later from the same IP (`timingSafeEqual`) |
| Turnstile | Headless bots and token reuse | Verified server-side with `siteverify` (secret + `remoteip`); `success`, `hostname` (our domains only) and `action === "contact"` must all match; tokens are single-use and reset after each attempt |
| Rate limit | Floods from one visitor | 5 per hour and 20 per day per `SHA-256(ip + IP_HASH_SALT)`, 429 + `Retry-After`. **Why this design:** it counts the `contact_messages` rows themselves (no extra table, no clean-up job, only messages that passed every other check count) inside one SQL function, `contact_submit`, under a per-IP `pg_advisory_xact_lock`, so parallel requests cannot race past the limit |
| Storage | Anonymous reads of messages | `contact_messages` has RLS enabled and forced with **no policies**, and table/function privileges are revoked from `anon`/`authenticated`; only the server's service-role key (server-only env var) can read or write. Raw IPs are never stored |
| Email | Spam relay, spoofing | Gmail SMTP over TLS (465) with an App Password; the recipient is fixed (`CONTACT_TO`); the visitor's address is only the **Reply-To**, never From; nodemailer runs with file and URL access disabled |
| Errors and logs | Information leaks | Generic JSON errors (`server_error`, `forbidden`, …); field messages only for validation; logs are one JSON line with `event`, `status`, `reason`, `ms` (no names, emails, IPs, hashes, tokens or env values) |
| Configuration | Half-configured deploys | Any missing env var (or a salt under 32 characters) → 503 `not_configured`; the form then shows the email link |

**Why there is no auto-reply to visitors.** The "From" address of an auto-reply would be Umer's Gmail and the "To" address would be whatever the visitor typed, so anyone could make the site send email to any address (a spam relay and a harassment tool), each one costing Gmail quota and sender reputation. The on-page success message gives the visitor the same confirmation without that risk.

**Secrets.** Only `VITE_TURNSTILE_SITE_KEY` is public (Turnstile site keys are public by design). A test builds the site and fails if any other env name from `.env.example`, or any value from the local `.env`, appears in the bundle (values are never printed). `IP_HASH_SALT` was generated as 48 random bytes and written straight into `.env`.

**CSP (vercel.json, all routes):** `default-src 'self'; script-src 'self' 'wasm-unsafe-eval' https://challenges.cloudflare.com; style-src 'self'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self' blob: https://challenges.cloudflare.com; media-src 'self' blob:; worker-src 'self' blob:; frame-src https://challenges.cloudflare.com; manifest-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`, plus `Cross-Origin-Opener-Policy: same-origin`. `'wasm-unsafe-eval'` is for the Draco decoder (WebAssembly, not JS eval); `blob:` is for the Draco worker, GLB textures (GLTFLoader fetches them as Blob URLs) and images. zod runs in jitless mode so it never probes `new Function`. Verified with `node scripts/csp-check.mjs` (vite preview with these exact headers + Chrome): zero violations across Classic, the opening, sound, a project video, the form with Turnstile, and Explore on WebGPU and WebGL2.

## 1b. Chat system "Ask my AI" (P5): design and controls

**Flow.** Browser (Classic `#chat` or the Explore Saloon case file, one component, lazy chunk) → `GET /api/chat-token` (Turnstile once, action `chat`, token in the `X-Turnstile-Token` header) → 1-hour HMAC session → `POST /api/chat` (Vercel Function, bom1, `maxDuration` 15 s). The knowledge base is built offline by `npm run rag:ingest` from `/content` (15 documents, 20 chunks).

| Stage | What it stops | How |
|---|---|---|
| Request checks | Probing, cross-site use, memory abuse | POST only, JSON only, ≤ 8 KB while streaming, same-origin allow-list (same helper as the contact form), no CORS headers |
| Shared zod schema | Malformed input, forged turns | Message 2–500 characters, history ≤ 6 turns of ≤ 500 characters with roles restricted to `user` / `assistant`, language `en` / `ur` / `roman`, every control character and the CR / Unicode line separators refused, unknown keys refused; the same schema runs in the browser |
| Session token | Bots calling the LLM directly | `GET /api/chat-token` verifies Turnstile once (success + hostname + action `chat`), then issues `expiry.HMAC-SHA256(expiry, hashed IP)` keyed with `IP_HASH_SALT`; every `POST /api/chat` must carry a valid one (1 hour, not valid from another IP), checked before any database or model call (401) |
| Rate limit and daily cap | Floods; running out of free quota | `chat_submit()` in SQL: 20 questions per rolling 10 minutes per salted IP hash (429 + `Retry-After`) and a global daily cap `CHAT_DAILY_CAP` (503 "the AI is resting today"), both under advisory locks so parallel requests cannot race past them |
| Injection screen | Direct and indirect prompt injection | Heuristic list (English, Roman Urdu, Urdu script) on the message and every user turn in the history, then **Llama Prompt Guard 2 86M** on Groq (multilingual; the 22M model missed the Urdu test attack) on the message and the whole history; a score ≥ 0.9 → a fixed polite refusal, `flagged = true` in `chat_logs`, and the text never reaches the answering model. If Prompt Guard is unreachable the heuristics and the prompt rules still apply |
| Private-data screen | Phone number, address, CNIC | Requests for them get a fixed reply that offers only the public email and the contact form; the model is never called |
| Retrieval | Answers from outside the case files | The query is embedded (Gemini `RETRIEVAL_QUERY`, 768-d, normalised) and matched with `match_chunks()` (vector + full-text, RRF k = 60, top 6); only the top 5 passages, trimmed to ~1,200 characters, are sent to the model |
| Relevance gate | Calling the LLM for plainly unrelated questions | Best similarity below `RAG_MIN_SIMILARITY` (0.55) → "That's not in my case files…" with no LLM call. **Measured limit:** similarity alone does not separate the unanswerable questions (they score 0.52–0.70 against 0.62–0.77 for answerable ones, because the whole index is about one person), so the gate is a cheap pre-filter and the grounded prompt carries the real refusal (see eval) |
| Grounded prompt | Invention, instruction override, leakage | First-person twin that may use only the numbered CONTEXT, must cite `[n]`, must say it does not know, keeps tenses true to the sources, replies in the user's language, never reveals or paraphrases its instructions, never gives private data, and treats the CONTEXT, the history and the question as untrusted data (they sit in delimited blocks) |
| Output filter | Private data and malicious links in answers | Phone and CNIC patterns and every email except the public one become `[removed]`; only links to same-page anchors, `github.com/muhammadumerfarooqq` and `linkedin.com/in/mumerfarooq04` survive; `[n]` citations are normalised, unknown numbers dropped and renumbered to the sources actually used (one page cited twice is merged) |
| Rendering | XSS | The client builds the answer from text nodes and `createElement` only (no HTML sinks, tested); source chips link only to validated `#anchor` values |
| Resilience | Provider outages and free-tier limits | Groq `openai/gpt-oss-120b` (7 s cap) → Gemini `gemini-3.5-flash` (4.5 s) → Groq `qwen/qwen3.8-27b`, inside a 13.5 s budget; if all fail, a generic 502. Model ids were taken from each provider's live `/models` list on 18-Nov-2026 |
| Logging and retention | PII in logs; indefinite storage | Console logs hold only event / status / reason / milliseconds. `chat_logs` stores the question (≤ 500 characters, kept for answer-quality evaluation), the language, the sources, a refusal / flagged flag, the model, the latency and a salted IP hash; no raw IP, no cookie, no account. Retention is until deleted in the Supabase dashboard; an automatic purge is planned (LIMITATIONS) |
| Keys | Secret exposure | `GEMINI_API_KEY` and `GROQ_API_KEY` are read from `process.env` on the server only and travel in headers (`x-goog-api-key`, `Authorization`), never in a URL; a test fails if their names, their values or the provider endpoints appear in the bundle |

**What the model can and cannot do.** It has no tools, no write access and no network access of its own: the only side effects of a question are one `chat_hits` row and one `chat_logs` row written by the server.

**Why a fixed refusal instead of asking the model to refuse.** Injection and private-data requests are answered by constant text chosen by the server, so a cleverly worded attack cannot talk the model into anything: the model is never reached.

## 1c. Voice input and read-aloud (P6): design and controls

**Flow.** Microphone button in the chat (Classic `#chat` and the Explore Saloon, same module) → `MediaRecorder` (≤ 30 s, 32 kbps) → `POST /api/transcribe` with the chat session in `X-Chat-Session` and the language in `X-Chat-Lang` → Groq Whisper → the same injection and private-data screens as typed text → `{ text }` or a fixed refusal → the text appears in the input; the visitor checks it and presses Send (an ordinary `/api/chat` question with its own checks). Read aloud is entirely in the browser (`speechSynthesis`).

| Stage | What it stops | How |
|---|---|---|
| Request checks | Probing, cross-site use, non-audio uploads, memory abuse | POST only, same-origin allow-list, four audio content types, 2 MB cap before and while reading, the bytes must carry the claimed container's signature |
| Length | Long recordings burning quota | The browser stops at 30 s; the server refuses a WAV over 30 s from its header and any file over 30 s from Whisper's own duration (partial, see L200) |
| Session + limits | Bots and floods | Chat session (Turnstile once), `stt_submit()` 10 per 10 minutes per salted IP hash, the shared `CHAT_DAILY_CAP`, advisory locks |
| Whisper | Wrong language, invented text | Language hint from the selector (none for Roman Urdu), `temperature 0`, style prompt discarded if echoed, no-speech score check |
| Transcript screens | Spoken prompt injection, spoken private-data requests | Heuristics + Prompt Guard 2 on the cleaned text; fixed replies; the text of an attack is not returned |
| Confirmation | A mis-heard or hostile transcript becoming a question without the visitor knowing | The text is only put in the input; Send is a separate press |
| Storage and logs | Voice data retention | No file, table or cache holds audio or text; logs hold metadata only |
| Browser | A microphone left on, XSS | Tracks stopped when recording ends or the panel / tab goes away; `Permissions-Policy: microphone=(self)`; text nodes only |

**What can and cannot happen.** The only side effects of a recording are one `chat_hits` row (kind `stt`) and one Whisper call; the model has no tools. A visitor who denies the microphone keeps the full text chat.

## 6. Limitations

- *(Historical, SOLVED in P4: see C10)* **No Content-Security-Policy yet.** It is built in P4/P11 when the Turnstile and Supabase origins are known. Until then the site is protected against framing, sniffing and downgrade, but not against injected scripts. The site currently has no user-supplied content and no scripts of substance.
- *(Historical, SOLVED in P4: the policy grants exactly these, plus `connect-src blob:` for GLB textures)* **Explore's CSP needs (for the P4/P11 policy).** WebGPU needs no CSP directive. The Draco decoder is WebAssembly, so `script-src` will need `'wasm-unsafe-eval'` (not `'unsafe-eval'`); DRACOLoader runs it in a worker created from a Blob URL, so `worker-src blob:` (or `'self' blob:`); GLTFLoader turns embedded textures (the baked town's WebP) into Blob URLs, so `img-src 'self' blob:`; models, `town.json` and the `.wasm` are fetched, so `connect-src 'self'`. Since P3.2 the baked town, the Draco avatar and the train use both the Blob worker and Blob images. KTX2/Basis is not used, so no transcoder is shipped. P3.2 adds no new directive: the train and its JSON are same-origin (`connect-src 'self'`), the case-file dialog is plain DOM, and the interview draft uses the Clipboard API, which needs no CSP directive and is not restricted by the current `Permissions-Policy` (`clipboard-write` is not listed).
- **Strict install-script policy only protects the install step.** It does not make a pinned package trustworthy; it only stops it from running code during install without review. A compromised pinned version would still run when imported.
- **`allowScripts` and `strict-allow-scripts` need a recent npm** (this project was set up with npm 11.16). Older npm versions ignore them. `engines.node >= 24` is the guard.
- **HSTS `preload`** is declared, but the domain is only on the browser preload list if it is submitted separately. Do not submit a `*.vercel.app` hostname.
- **Tests check configuration, not behaviour on the live site.** Live header verification happens in P11.
- **The Blender MCP socket is unauthenticated.** Moved to the risk register as **R5** (section 7). *Historical: closed 9-Nov-2026 when the Blender MCP was retired.*
- **The After Effects server path in `.mcp.json` is machine-specific** (`D:/PROJECTS/tools/...`). On another machine the server simply fails to start; it is a local authoring tool, not part of the site. The commit pin lives in the clone, not in this repo, so after any `git pull` in the clone the review and audit must be repeated before use.
- *(Historical, Blender MCP retired 9-Nov-2026)* **`.mcp.json` pins the server package, not its dependencies, and the add-on is installed separately.** `uvx` fetches `mcp-for-blender@2.2.6` from PyPI without hash checking, and the add-on inside Blender was installed by hand from the same version. They are not tied together by the repo; if one is upgraded the other should be too.
- *(Historical, Blender MCP retired 9-Nov-2026)* **Blender MCP telemetry is not fully off.** `disable_telemetry` stops collection of prompts, code, screenshots and scene data, but the server still sends minimal anonymous usage counts (tool name, success, duration). The tool cannot turn these off. They contain no project content. Removing them entirely would mean blocking the server's outbound traffic at the firewall, which has not been done.
- **The dev server exposes more than production.** `npm run dev` serves any file under the repo (including `blender/exports/` and `node_modules/`) to `localhost`, which is how spike pages load their models. It binds to localhost only (no `--host`), and none of this is in `dist/`.
- Admin and chatbot controls do not exist yet (P5, P7). The contact system's live behaviour (real email, 429 on the 6th message, anon key refused) is verified by Umer after pasting the SQL and adding the Vercel env vars (LIMITATIONS L178).
- **Chat answers come from free-tier LLM providers** (Groq, Gemini) and can be wrong or unavailable; the 20-question evaluation measures accuracy and the fallback chain covers outages, but no model is perfect. Questions in `chat_logs` have no automatic retention purge yet (LIMITATIONS).
- **Turnstile is a third-party script** on the form (L174): accepted; it loads only when the form is on screen, and it is the only third-party origin the CSP allows.

## 9. Plain-English explainer

- **Secrets.** Passwords and API keys live in a file called `.env` that git is told to ignore, so it can never be uploaded by accident. `.env.example` is a fill-in-the-blanks form with the names of the secrets but none of the values. Anything starting with `VITE_` is deliberately public (it ends up in the website's code), so only harmless values get that prefix.
- **Security headers.** These are instructions the server sends to the visitor's browser: always use HTTPS, do not guess file types, do not let other sites put this page inside a frame, share only the minimum in the referrer, and only allow the microphone on this site (needed for voice chat later).
- **Supply chain.** Our site is built from code written by other people (npm packages). A malicious update could steal data when installed. We reduce the risk by fixing exact versions, so nothing changes without us noticing, and by refusing to let packages run install-time scripts until a human has reviewed them.
- **Content is checked before it goes live.** The text on the site comes from simple files in `content/`. When the site is built, each file is checked against a strict list of allowed fields. Any HTML or dangerous link hidden inside is shown as harmless text instead of running. If a phone number, ID-card number or email address slipped in, the build simply stops and says which file and line. The chatbot will later learn from the same files, so this check also keeps private details out of its answers.
- **A page with no hidden doors.** All of the site's code lives in separate files that we wrote and reviewed. There are no snippets of script tucked inside the HTML, and nothing is loaded from other companies' servers: no font services, no CDNs. That means a strict browser rule can later say "only run code from this website", and visitors aren't tracked by third parties just by opening the page. The only things the site remembers in the browser are "light or dark" and "sound on or off"; anything else found there is ignored. Visitors who ask their device to reduce motion get a calm, fully visible page.
- **The AI twin only reads my case files.** When you ask a question, the site first checks you are a person (one quick Cloudflare check), then looks up the few passages of this site that are closest in meaning to your question and hands only those to a language model with strict rules: use only these passages, cite them, say "not in my case files" if the answer is not there, never give private details. Questions that try to trick it, or that ask for a phone number, never reach the model at all: the server answers them with a fixed sentence. Answers are shown as plain text, links are limited to this page, my GitHub and my LinkedIn, and there is a daily limit so the free AI services do not run out.
- **AI tools on the development computer (After Effects MCP).** Claude Code can drive After Effects through a small helper program that is pinned to a version we reviewed and cannot be reached from the network. The weak spot is that other programs on the same computer could talk to it too, so we switch it on only while working and off afterwards. The Blender helper was retired on 9 November 2026: the avatar is now built from scripts, so that door is closed. The risks we knowingly accepted, and why, are listed in the risk register (section 7).
